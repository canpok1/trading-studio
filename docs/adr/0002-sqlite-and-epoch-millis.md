# 0002. DB に SQLite を使い、時刻を UTC のエポックミリ秒の整数で持つ

- ステータス: 採用
- 日付: 2026-09-25

## コンテキスト

利用者は1人で、自宅サーバー（mini-pc）の1コンテナで動かす。取引の記録は失うと取り返しがつかないため、バックアップや別環境への持ち運びを簡単にしたい（Issue #1・#4）。

戦略は決定論で動かす（同じ入力なら同じ結果）。時刻の比較・並べ替えが表記やタイムゾーンの解釈で変わると、この前提が崩れる。

## 決定

- DB は SQLite。ファイル1つで持ち、既定は `data/trading-studio.db`（環境変数 `DB_PATH` で変更）
- アクセスは Drizzle ORM と `bun:sqlite`。テーブル定義から `drizzle-kit generate` で SQL を作ってコミットし、サーバー起動時に未適用分を適用する
- 接続時に WAL モード・外部キー制約・ロック待ち（5秒）を設定する
- 未適用のマイグレーションがあるときは、適用前に `VACUUM INTO` で `data/backup/` へ DB を書き出す。適用に失敗したらサーバーを起動しない
- 時刻は UTC のエポックミリ秒の整数で持ち、表示時に JST へ変換する

## 結果

- DB ファイルをコピーするだけで持ち運べる。サーバーのプロセスを別に立てなくてよい
- 同時に書き込めるのは1つだけ。ロック待ちで吸収できる程度の書き込み量を前提にしている
- 時刻の比較・並べ替えが整数の比較になり、速く、解釈違いが起きない。代わりに DB を直接見たときに人が読みにくい
- マイグレーションは Drizzle が1トランザクションで適用するため、失敗しても途中の状態が残らない。SQLite では `PRAGMA foreign_keys` をトランザクション内で切り替えられないため、テーブルを作り直す変更では外部キー制約に注意が要る

## 検討した代替案

- PostgreSQL などのサーバー型 DB：同時書き込みに強いが、コンテナとバックアップの手間が増える。利用者1人には過剰
- 時刻を ISO 8601 の文字列で持つ：人が読みやすいが、表記の揺れ（タイムゾーンの書き方・小数秒の桁）で比較を誤りやすい
