# 0015. 採点の基準の改善は、過去記事を版ごとに採点し直してバックテストで確かめ、使い始める時刻は運用の採点時刻を引き継ぐ

- ステータス: 採用（バックテストで記事を使い始める時刻は `0023` で公開時刻 + 取得の間隔に変更）
- 日付: 2026-09-30

## コンテキスト

採点の基準（プロンプト）を改善したとき、その効果をバックテストで確かめたい。

- 判定に記事を使い始める時刻は採点時刻にしている（2026-09-27 に決定）。公開時刻にすると、取得の間隔（既定15分）・採点の待ち・失敗の再試行（数時間）・取得元を足した直後（最大24時間）の分だけ、バックテストが実際より早くニュースを知っていたことになり、成績が甘く出るため
- 採点は記事ごとに1件で、採点し直すと上書きされる。過去の記事を新しい基準で採点し直すと、採点時刻が「今」になり、過去の期間のバックテストに入らない。元の採点も消えて新旧を比べられない

## 決定

- 過去の記事を、保存済みの版を指定して採点し直す。結果は記事と版の組ごとに別の表（`news_rescores`）に持ち、運用の採点は上書きしない
- 採点し直した記事を判定に使い始める時刻は、運用で最初に採点した時刻を引き継ぐ。運用で採点されなかった記事は、版を指定しても使わない
- バックテストで市場評価に使う採点の版を選べるようにする。既定は「運用どおり」（今までと同じ）
- 版を指定したとき、期間の市場評価に使う記事にその版の採点が無いものがあれば実行しない（利用者の判断、2026-09-30）。採点し直しに失敗して止まった記事は除いて実行する

## 結果

- 運用と同じ遅れのまま、新旧の版を同じ期間・同じ記事で比べられる
- 採点し直す件数ぶん Gemini を呼ぶ。1件5秒以上空けるので、1000 件で1時間半ほどかかる。新着の採点を優先する
- 版は採点の基準の文面だけを表す。採点し直すときのモデルはそのときのモデルで、運用で採点したときのモデルと違うことがある

## 検討した代替案

- 使い始める時刻を公開時刻にする: 上記の遅れの分だけ先取りする。採点し直しが上書きされる問題も残り、目的を満たさない
- 採点し直した記事だけ公開時刻（または取得時刻）から使う: 新しい版だけ採点が早い前提になり、比較で新しい版が有利になる
- 版の採点が無い記事を除いて実行する: 記事が減った分だけ評価が中立に寄り、成績の差が版の違いによるのか記事の数によるのか区別できない
- 版の採点が無い記事を古い版の採点で補う: 版が混ざり、新しい版の効果を測れない
