# 0007. 約定は Coincheck の公開 WebSocket で受け、つながった直後は公開 API の直近100件で補う

- ステータス: 採用
- 日付: 2026-09-26

## コンテキスト

フェーズ2で、Coincheck の BTC/JPY の約定から1分足を自前で作って貯める。収集はサーバーが動いている間は常に行い、デプロイのたびにコンテナが再起動する（ADR 0003）。再起動や切断の後にどこまで遡って補えるかを調べた（2026-09-26）。

確認した仕様（出典: [取引所 API ドキュメント](https://coincheck.com/ja/documents/exchange/api)。「実測」は 2026-09-26 に実際に呼んで確かめたもの）:

- 公開 WebSocket `wss://ws-api.coincheck.com` の `btc_jpy-trades` チャンネルで約定が届く。1件は `[約定時刻(秒), 約定ID, 取引ペア, レート, 量, 注文方法, TakerID, MakerID, 板寄せID]` の配列で、0.1秒間隔でまとめて届く。認証は不要。公式は自動再接続の実装を推奨している
- 板寄せのときは売り買い双方が配信され、合算した量は実際の取引高と一致しない（公式の注記）。同じ約定 ID で届くかは未確認
- 公開 API `GET /api/trades` は最新の約定を返す。1回で最大100件（実測: `limit=1000` でも100件）。ページングの `starting_after` / `ending_before` は「now unavailable」のエラーになる（実測）。遡れるのは直近100件だけで、2026-09-26 の相場では約10分ぶん
- 約定の時刻は秒単位。価格は円の小数表記（`"13232405.0"`）、量は BTC の小数表記（`"7.0e-08"` のような指数表記もある）
- 公開 API・公開 WebSocket の呼び出し回数の制限は、ドキュメントには新規注文（秒間4回）しか書かれていない
- 非公式の `GET /api/charts/candle_rates` は直近300本の1分足（5時間ぶん）を返す（実測）が、ドキュメントに載っていない
- 利用規約（2024-07-24 版）第11条(6) は、取引所 API を「取引所API概要」に従って使うよう定めている。自動での取得を禁じる条項は見当たらない
- この実行環境（Claude Code on the web）からは WebSocket へつなげず、実際の配信は確かめていない

## 決定

- 常時は公開 WebSocket の `btc_jpy-trades` で約定を受ける。`btc_jpy-orderbook` も購読し、届いたことを接続が生きている印にする
- つながった直後は `GET /api/trades` の直近100件で遡れる範囲を補う。補えない分は欠損として残す
- 非公式の `candle_rates` は使わない（2026-09-26 ユーザー判断）
- 切断・無通信（60秒）・購読が始まらない（30秒）ときは、1秒から倍々で延ばし上限1分の間隔でつなぎ直す
- 同じ約定 ID は1回だけ数える

## 結果

- デプロイの再起動程度の短い停止（約10分以内）は埋まる。それより長い停止は欠損として残る
- 公式のドキュメントにある手段だけを使うので、利用規約との関係がはっきりしている
- 板寄せの約定が別々の ID で届く場合、その分の出来高は実際より多くなる（推測。未確認）

## 検討した代替案

- 非公式の `candle_rates` で5時間まで補う: 長い停止も埋まるが、ドキュメントに無く予告なく変わりうる。規約が求める「取引所API概要」に従った使い方か不確か。通常の停止はデプロイの再起動で1分未満のため見送った
- 公開 API を定期的に呼ぶだけにする: 100件の上限を超える前に呼び続ける必要があり、急変時に取りこぼす。WebSocket のほうが遅れも少ない
