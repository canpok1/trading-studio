# 0027. Gemini 直結に加えて OpenAI 互換の接続先を持ち、モデルを選ぶと接続先も決まるようにする

- ステータス: 採用（切り替えの単位・一覧の取得・スキーマの変換はユーザー確認済み: 2026-10-11）
- 日付: 2026-10-11

## コンテキスト

採点とアドバイスは Gemini の generateContent を直接呼んでいる。Gemini 以外の AI も使いたいが、AI ごとに個別対応すると改修がかさむ。自宅サーバーの他のサービスでも AI を使うため、AI の API を集約するサービス（Bifrost を予定。構築は別で進める）を立て、trading-studio はそこを OpenAI 互換 API で呼びたい。Gemini 直結は残したい（利用者）。

使い方の前提:

- 採点（設定→ニュース）とアドバイス（設定→バックテスト）で、モデルを別々に選んでいる
- 応答の形は構造化出力（Gemini の responseSchema の書き方）で強制し、受け取った後もアプリ側で検証している
- 集約サービスの `/models` は、つないだ全プロバイダーのモデルを返すので数十件以上になりうる

## 決定

- 接続先は「Gemini 直結」と「OpenAI 互換」の2つ。採点・アドバイスのモデルの一覧を両方の合算にし、選んだモデルの接続先で呼ぶ。OpenAI 互換のモデルは `openai:` を付けて保存・記録し、Gemini のモデル名と区別する
- OpenAI 互換の接続先は URL と API キー（任意）を設定画面の「全般」で保存する。キーの扱いは Gemini と同じ（`0009`）
- OpenAI 互換のモデルの一覧は接続先の `/models` から取り、具体名をアプリに持たない。選択欄は入力で絞り込めるようにする。Gemini 直結は今の固定の3モデルのまま
- 応答の形の定義は Gemini の書き方のまま持ち、OpenAI 互換へ送るときだけ標準の JSON Schema に変換して `response_format: json_schema` で送る。`strict` は使わない

## 結果

- AI の追加は集約サービス側の設定だけで済み、trading-studio の改修は要らない
- 採点は Gemini 直結のまま、アドバイスだけ集約サービス経由、のように用途ごとに接続先を変えられる
- 呼び出しの経路が2つ残る。集約サービス経由の Gemini で問題が無ければ、直結を消して1つにできる
- 集約サービスが止まっていると一覧を取れない。保存済みのモデルはそのまま表示・使用する
- `strict` なしの構造化出力は、AI によって形を守らないことがある。これまでどおり受け取った後の検証で弾き、失敗として再試行する
- 本物の集約サービスへの呼び出しはこの実行環境で確かめていない（偽のサーバーで送信内容を確かめた）

## 検討した代替案

- 全体を Gemini／OpenAI 互換で一括で切り替える: 設定は1つで済むが、採点とアドバイスを別の接続先にできず、切り替えのたびにモデルも選び直しになる
- OpenAI 互換のモデル名を手で登録する: 一覧が短く保てるが、打ち間違いやすく、具体名を持つことになる（利用者が却下）
- 定義を JSON Schema に書き直し、Gemini にも JSON Schema（`responseJsonSchema`）で送る: 定義は1つになるが、動いている Gemini 直結の挙動（項目の順序など）が変わりうる
- Gemini 直結のモデルも一覧を取得する: 具体名を持たずに済むが、採点の既定モデルが無くなり挙動が変わる。今回は見送った（利用者の判断）
- `strict: true` で送る: 形の保証は強いが、改善版の戦略は任意の項目が多く「全項目必須・追加の項目禁止」の制約に合わない
